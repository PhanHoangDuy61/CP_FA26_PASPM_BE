Whether that person is the formal PO, or whether a named PO sign-off is still required by the project, is an **administrative verification that is still outstanding** (column "PO identity"). It does not prevent implementation and testing on a feature branch. It does block `RELEASE_ACCEPTED`.

## Release-readiness vocabulary (2026-11-02 (c))
The four register statuses map onto the release record in the [readiness report](../reports/F05_D8_D9_D10_RELEASE_READINESS_2026-11-02.md) as: `BUSINESS_CHOICE_CONFIRMED` = column 3; `TECHNICALLY_VERIFIED` = `IMPLEMENTED` + `TESTED` for the stated environments (local; native Linux and GitHub CI are separate rows and are **not run**); `RELEASE_SIGNOFF_PENDING` / `RELEASE_APPROVED` = column `RELEASE_ACCEPTED`. The release record has empty approver, decision and date fields; **nothing is `RELEASE_APPROVED`**.

## Rules that still hold
- Ordinary development and production configurations do **not** enable scheduling: `paspm.mining.schedule-dispatch-enabled` defaults to `false`, activation answers 503, no background thread starts.
- An opt-in local acceptance pass is **not** a public release. `RELEASE_ACCEPTED` needs the outstanding items above.
- Anything that changes an approved choice must be recorded here with the date and the source of the confirmation.
