# F02 Product and Inventory API Contract

## Current contract update — 2026-11-19

This backend-only update keeps existing routes and response bodies and adds an expiry-date clear action. Product and batch IDs are generated by the database: do not send them in create requests; use the returned `id` for navigation and subsequent edits. Product sorting supports `name`, `sku`, `category`, `unit`, `costPrice`, `sellingPrice`, `status`, `requiresExpiry`, and `stockQuantity`, with `productId ASC` as a stable tie-breaker.

SKU is trimmed and uppercased before persistence and duplicate checks; uniqueness remains Store-scoped. Duplicate SKU returns `409` with a clear message. Product names are not unique: an exact match, or a one-character edit for normalized names of at least four characters, after case/whitespace normalization returns `409` with `code: "PRODUCT_NAME_CONFIRMATION_REQUIRED"` and `confirmWith: "confirmSimilarName=true"`. Ask the user to confirm, then retry the same POST/PUT with `"confirmSimilarName": true`; the initial response does not create or update a product.

Batch PATCH can set `expiryDate` in addition to remaining quantity, status and push day. Omitted or JSON `null` `expiryDate` means unchanged. Use `DELETE /api/inventory-batches/{id}/expiry-date` to clear it; clearing is rejected for `requiresExpiry=true` products. `batchCode`, `receivedAt` and `initialQuantity` remain immutable through PATCH.

## SKU and batch-code formats

Product create/update trims and uppercases SKU before persistence. No fixed SKU pattern is imposed; SKU uniqueness is scoped to the Store.

Batch create no longer accepts `batchCode`; sending it is an unknown-field 400. The backend returns a generated code in the existing `BatchView.batchCode` response field: `BATCH-YYYYMMDD-NNN`, where the date is `receivedAt` in the configured Store time zone and the sequence is monotonically incremented per Product across dates, padded to at least three digits. The Product row is locked during generation so concurrent creates for the same Product receive distinct sequence values. Batch codes remain immutable after creation. This request-body change requires clients that previously sent `batchCode` to remove it; routes and response fields are unchanged.

> **2026-11-16:** Product `expiryPushDays` is **removed** from `ProductRequest` and `ProductView` (sending it → 400) and V26 drops the column — see the last section. *2026-11-15 (history):* batches accept `pushDay`; Product `expiryPushDays` was deprecated and ignored (P5). Statements below that call `expiryPushDays` the F03 threshold are **legacy (v1.2)**.

## Legacy v1.2 Product expiry priority update (2026-10-19; removed 2026-11-16)

The existing Product POST/PUT request accepts optional `expiryPushDays: integer|null`; absent/null is stored as0, values must be >=0, and fractional/string/boolean values are rejected400. Full PUT must send the desired threshold (omitting resets it to0). Product GET/list/create/update/status responses include `expiryPushDays: integer`. Store Admin owns this field in their Store; Merchandiser and System Admin cannot modify it through F02, and cross-Store records return404. No duplicate configuration endpoint was added. `requiresExpiry=false` remains NOT_APPLICABLE in F03 even if a threshold is configured. Inventory quantities are unchanged by threshold updates.

F03 uses only this Product threshold: no Store fallback. The legacy Store expiry-window endpoint is deprecated. New E is binary from the earliest-expiring ACTIVE positive-quantity batch with expiry strictly after the analysis date. Batch expiring today is not sellable in the current summary. `GET /api/utility/expiry-push-batches` provides a Store Admin/Merchandiser current push view independently of mining; see the F03 contract.


Contract checked against the running OpenAPI export, F02 ERD and current Backend source on 2026-11-19. Every route requires a bearer JWT. Resources are scoped to the authenticated Store; request bodies cannot choose a Store. Cross-Store product/category/batch access is returned as 404. F02 does not delete Products or Categories and does not expose stock-movement APIs; batch DELETE routes only clear optional dates.

### Permissions

| API group | Allowed role |
|---|---|
| `GET /api/categories`, `GET /api/categories/{id}` | `STORE_ADMIN`, `MERCHANDISER` |
| All other `/api/categories...` operations | `STORE_ADMIN` |
| `GET /api/products`, `GET /api/products/{id}` | `STORE_ADMIN`, `MERCHANDISER` |
| Product create/update/status and inventory-summary operations | `STORE_ADMIN` |
| Batch list/create/detail/PATCH and `DELETE .../push-day` or `DELETE .../expiry-date` | `STORE_ADMIN` |

Unauthenticated requests return 401; authenticated requests with a disallowed role return 403. Foreign or absent Store-scoped resources return 404 after role authorization.

The approved ERD is `docs/diagrams/PASPM_Complete_ERD_F02_Inventory_Batch_v3.drawio` (moved from the former `docs/ERD_Diagram/`). The schema uses `INVENTORY_BATCH`, not `PRODUCT_LOT`. Product stock is derived from batch remaining quantities.

## DTOs

- `CategoryRequest`: required nonblank `name:string` max150 and `status:string` in `ACTIVE|INACTIVE`.
- `CategoryView`: `{id:int32,name:string,status:string}`.
- `ProductRequest`: required `sku:string`, `name:string` max180, `unit:string` max40, `requiresExpiry:boolean`, `sellingPrice:number >= 0`, `costPrice:number >= 0`, `status:ACTIVE|INACTIVE`; nullable/optional `categoryId:int32` and optional `confirmSimilarName:boolean`. SKU is trimmed and uppercased before persistence; Do not send an ID, Store ID, stock or F03 score fields.
- `ProductView`: `{id:int32,sku:string,name:string,unit:string,requiresExpiry:boolean,category:CategoryView|null,sellingPrice:number,costPrice:number,status:string,stockQuantity:int64}`. `id` is database-generated; `stockQuantity` is derived from all batch remaining quantities and read-only.
- `ProductPage`: `{content:ProductView[],page:int32,pageSize:int32,totalElements:int64,totalPages:int32}`.
- `BatchCreateRequest`: required `receivedAt:string` ISO date-time and `initialQuantity:int32 > 0`; nullable/optional `expiryDate:string` ISO date and `pushDay:string` ISO date. Do not send `batchCode` or an ID. Expiry required if Product `requiresExpiry=true`.
- `BatchPatchRequest`: optional `remainingQuantity:int32 >= 0`, `status:ACTIVE|BLOCKED`, `pushDay`, and `expiryDate`; at least one non-null field must be supplied. Remaining may not exceed initial quantity. Null/omitted date fields mean unchanged; use DELETE routes to clear them.
- `BatchView`: `{id:int32,productId:int32,batchCode:string,receivedAt:date-time,expiryDate:date|null,initialQuantity:int32,remainingQuantity:int32,status:string,createdAt:date-time,updatedAt:date-time,pushDay:date|null}`. ID and `batchCode` are backend-generated/read-only. New batches start `remainingQuantity=initialQuantity`, `status=ACTIVE`.
- `InventorySummary`: `{productId:int32,totalQuantity:int64,sellableQuantity:int64,expiredQuantity:int64,blockedQuantity:int64,expiringSoonQuantity:int64}`.

Product list query parameters: `search` default empty; `categoryId` optional int32; `status` default empty (`ACTIVE|INACTIVE` when nonempty); `page` default0, >=0; `pageSize` default20, 1..100; `sortBy` default `name`, supported `name|sku|category|unit|costPrice|sellingPrice|status|requiresExpiry|stockQuantity`; `sortDirection` default `asc`, supported `asc|desc`. Search matches name or SKU without case sensitivity. Invalid sort gives 400. Ties use `productId ASC`, regardless of requested direction, to keep pagination stable. Page is zero-based. Unlike category and batch lists, product list returns pagination metadata in `ProductPage`.

SKU is trimmed and uppercased before storage/checking, and is unique per Store (database constraint); same normalized SKU may exist in another Store. Duplicate SKU returns `409` with `SKU already exists in this Store`, including database uniqueness races. An exact product name, or a one-character edit when the normalized names are at least four characters, in the same Store is not a uniqueness violation: create/update returns a `409 PRODUCT_NAME_CONFIRMATION_REQUIRED` warning until the client retries with `confirmSimilarName:true`. Category names have no uniqueness constraint in the current migration. A Product category is checked for Store ownership, but the service does not require that Category status is ACTIVE. Product status and category status are `ACTIVE|INACTIVE`; batch status is `ACTIVE|BLOCKED`. Category update is a full request replacement; Product PUT also requires the full `ProductRequest` body.

## Inventory rules

- `totalQuantity` sums every batch's remaining quantity, including blocked and expired stock. No batch yields zero.
- `blockedQuantity` sums batches whose status is `BLOCKED`.
- `expiredQuantity` sums ACTIVE batches with non-null expiry date on or before the Store-local current date.
- `sellableQuantity` sums ACTIVE batches with no expiry date or expiry date strictly after today. Expiry today is excluded under v1.2.
- `expiringSoonQuantity` sums ACTIVE batches with expiry date strictly after today through today + `expiringWithinDays`, upper boundary inclusive. It is part of sellable quantity and is not an additional disjoint bucket.
- Blocked and expired quantities do not overlap: expired calculation only considers ACTIVE batches.
- Time zone defaults to `Asia/Ho_Chi_Minh` (`paspm.store-time-zone`), configured at application level in current source, not per-Store.
- Summary SQL does not check Product status, so a deactivated Product's batches can still be counted as sellable by this summary. The frontend should display Product status separately.
- Batch quantity constraints: initial >0; remaining >=0 and <=initial. Receive sets remaining equal to initial. PATCH cannot change `batchCode`, `receivedAt`, or `initialQuantity`. `expiryDate` can be set by PATCH; JSON null/omission retains the date. `DELETE /api/inventory-batches/{id}/expiry-date` clears it only when the Product does not require expiry. `pushDay` must be on or before `expiryDate` when both are set. There is no adjustment history/stock-movement endpoint.
- Generated batch codes use the Store-local calendar date represented by `receivedAt` and a per-Product sequence that continues across dates (minimum three digits); the database uniqueness constraint remains the final safeguard. Older existing codes do not change.

## F02 / F03 ownership

F02 Product create/update owns `requiresExpiry`, SKU, category, unit, prices, and Product status. F02 batch APIs own batch expiry, push day and quantities. `stockQuantity` is derived and cannot be edited. The F03 API owns `stock_priority_score` and `seasonal_priority_score` through `/api/utility/products/{productId}/scores`; ProductRequest does not accept these fields. F03 derives expiry priority using inventory batches and a fixed analysis date. Do not add F03 score fields to F02 Product forms/contracts.

## Verification status and ERD differences

All 17 F02 method/path operations appear in the runtime OpenAPI document. `CatalogIntegrationTest` exercises authentication/role denial, category/product CRUD/status, Store isolation, batch CRUD, required expiry, quantity/status/date patch and date clearing. The OpenAPI document is generated from the runtime endpoint; no interactive Swagger UI session was run for this update.

OpenAPI does not encode nullable response fields: `ProductView.category` can be null when no category is assigned and `BatchView.expiryDate` can be null for a non-expiring Product, although its schema shows nonnullable object/date types. Treat these as nullable in TypeScript. The ERD labels the account table `USER`; the implemented schema uses `app_user` to avoid reserved-word issues. The ERD uses `CATEGORY` / `PRODUCT` / `INVENTORY_BATCH`, and migrations V1/V3 implement these entities, including Store-scoped unique SKU, composite Store/category ownership, and unique `(product_id,batch_code)`. No stored Product stock column exists. F03 migration V4 adds score columns separately; this is consistent with field ownership in the F03 utility API.

## Historical: 2026-11-15 — Batch push day (F03 Weight v2, Q1/P5)

- `BatchCreateRequest` adds optional `pushDay` (ISO date). `BatchPatchRequest` adds optional `pushDay`; it counts toward the "at least one field" rule, so `{"pushDay":"2026-12-01"}` alone is valid. `BatchView` returns `pushDay` (date or null).
- `pushDay` must be on or before `expiryDate` → otherwise 400 (also a database CHECK). PATCH cannot clear a push day (null means "not provided").
- Roles unchanged: Store Admin only for batch writes (Merchandiser 403); foreign batch → 404.
- `ProductRequest.expiryPushDays` / `ProductView.expiryPushDays` are **deprecated** (P5): still accepted, validated (≥ 0) and stored, but ignored by every calculation. F03 W2 uses `inventory_batch.push_day`.
- No backfill: existing batches have `pushDay = null` until the Store Admin sets it; F03 only warns (`MISSING_PUSH_DAY`). Tests: `PushDayIntegrationTest`.

## 2026-11-16 — Clear a batch push day (additive)
`DELETE /api/inventory-batches/{id}/push-day`: Bearer authentication, STORE_ADMIN only, caller's Store. No body. Returns HTTP 200 and the same `BatchView` as GET/PATCH with `pushDay: null`. Repeating on an already-clear batch succeeds without updating its timestamp. Unknown/foreign batch 404, wrong role 403, unauthenticated 401. Persisted quantity, status and expiry are unchanged. PATCH absent/null `pushDay` retains its value; only DELETE clears it. Future calculations report `MISSING_PUSH_DAY` for otherwise eligible batches.

## 2026-11-16 — `expiryPushDays` removed (DEC-20261116-02, V26)

- `ProductRequest` (create `POST /api/products`, full update `PUT /api/products/{id}`) no longer has `expiryPushDays`. The backend rejects unknown JSON fields, so a request that still sends it — any value, including `null` — gets **400** and nothing is written.
- `ProductView` (list, detail, create/update responses) no longer contains `expiryPushDays`.
- The JPA entity no longer maps the column, and migration V26 drops `product.expiry_push_days` together with `product.stock_priority_score` and `product.seasonal_priority_score` (and their CHECK constraints). Not reversible without a backup taken before V26.
- Use the batch `pushDay` (create, PATCH, `DELETE /api/inventory-batches/{id}/push-day`). Roles unchanged.
- Tests: `LegacyProductFieldsRemovedTest`, `LegacyProductColumnsV26MigrationTest` (H2 + MySQL), `PushDayIntegrationTest.productExpiryPushDaysIsRejectedAndScoringUsesBatchPushDays`.
