# F02 Product and Inventory API Contract

## Current contract update — 2026-11-24 (expiry boundary, push-day warning, product soft delete)

Rules: [DEC-20261124-01](../decisions/2026-11-24/DEC-20261124-01-batch-expiry-boundary-effective-status.md), [DEC-20261124-02](../decisions/2026-11-24/DEC-20261124-02-push-day-missing-warning.md), [DEC-20261124-03](../decisions/2026-11-24/DEC-20261124-03-product-soft-delete.md). Migration **V28**. All response changes are additive; no request field was added, removed or renamed.

- **Expired only after the expiry date.** A batch is expired only when today (`Asia/Ho_Chi_Minh`) is **after** `expiryDate`; on the expiry date it is still active and sellable. Expiry is never stored: the stored `status` stays `ACTIVE|BLOCKED` and is the only writable status (`PATCH` with `EXPIRED` or `INACTIVE` → 400).
- **`BatchView` gains three read-only fields** on every route that returns a batch:
  - `effectiveStatus: "ACTIVE" | "BLOCKED" | "EXPIRED"`. EXPIRED wins over BLOCKED; otherwise the stored status.
  - `daysToExpiry: int | null`. `expiryDate − today`; **0 on the expiry date**, negative when expired, null without an expiry date. "Expiring soon" = `effectiveStatus != "EXPIRED"` and `0 <= daysToExpiry <= 7`.
  - `warnings: string[]`. Always present. `["MISSING_PUSH_DAY"]` when the product `requiresExpiry`, `pushDay` is null and `effectiveStatus != "EXPIRED"` (stored status and remaining quantity do not matter). Saving is still allowed; the push day is never auto-filled.
- **`InventorySummary`** counts the same way and gains `batchesMissingPushDay: int64`. Buckets do not overlap: `expiredQuantity` = expired batches of any stored status; `blockedQuantity` = BLOCKED and not expired; `sellableQuantity` = ACTIVE and not expired; `expiringSoonQuantity` = ACTIVE with `0 <= daysToExpiry <= expiringWithinDays`.
- **`DELETE /api/products/{id}`** soft-deletes a product (STORE_ADMIN of the owning Store). See the endpoint table and "Product soft delete" below. The frontend must not compare dates itself any more.


## Current contract update — 2026-11-20

This backend-only update keeps existing routes, adds an expiry-date clear action, and changes Product SKU to backend-generated. Product and batch IDs are generated by the database; Product SKU is generated from its Product ID. Do not send `id` or `sku` in Product create/update requests; use returned values as read-only. Product sorting supports `name`, `sku`, `category`, `unit`, `costPrice`, `sellingPrice`, `status`, `requiresExpiry`, and `stockQuantity`, with `productId ASC` as a stable tie-breaker.

SKU is generated by the backend on create from the database-generated Product ID as `SKU-` followed by that ID padded to 11 digits. It is returned as read-only and cannot be supplied or changed through Product POST/PUT. Product names are not unique: an exact match, or a one-character edit for normalized names of at least four characters, after case/whitespace normalization returns `409` with `code: "PRODUCT_NAME_CONFIRMATION_REQUIRED"` and `confirmWith: "confirmSimilarName=true"`. Ask the user to confirm, then retry the same POST/PUT with `"confirmSimilarName": true`; the initial response does not create or update a product.

Batch PATCH can set `expiryDate` in addition to remaining quantity, status and push day. Omitted or JSON `null` `expiryDate` means unchanged. Use `DELETE /api/inventory-batches/{id}/expiry-date` to clear it; clearing is rejected for `requiresExpiry=true` products. `batchCode`, `receivedAt` and `initialQuantity` remain immutable through PATCH.

## Generated product SKU and batch-code formats

For a newly created Product with database ID `42`, the backend generates `SKU-00000000042`. Product IDs are globally generated by the database; the resulting SKU is also unique across Stores. Existing Product SKUs are preserved. Product creation and updates must omit `sku`; sending it is an unknown-field 400. Product updates keep the existing SKU unchanged.

Batch create no longer accepts `batchCode`; sending it is an unknown-field 400. The backend returns a generated code in the existing `BatchView.batchCode` response field: `BATCH-YYYYMMDD-NNN`, where the date is `receivedAt` in the configured Store time zone and the sequence is monotonically incremented per Product across dates, padded to at least three digits. The Product row is locked during generation so concurrent creates for the same Product receive distinct sequence values. Batch codes remain immutable after creation. This request-body change requires clients that previously sent `batchCode` to remove it; routes and response fields are unchanged.

> **2026-11-16:** Product `expiryPushDays` is **removed** from `ProductRequest` and `ProductView` (sending it → 400) and V26 drops the column — see the last section. *2026-11-15 (history):* batches accept `pushDay`; Product `expiryPushDays` was deprecated and ignored (P5). Statements below that call `expiryPushDays` the F03 threshold are **legacy (v1.2)**.

## Legacy v1.2 Product expiry priority update (2026-10-19; removed 2026-11-16)

The existing Product POST/PUT request accepts optional `expiryPushDays: integer|null`; absent/null is stored as0, values must be >=0, and fractional/string/boolean values are rejected400. Full PUT must send the desired threshold (omitting resets it to0). Product GET/list/create/update/status responses include `expiryPushDays: integer`. Store Admin owns this field in their Store; Merchandiser and System Admin cannot modify it through F02, and cross-Store records return404. No duplicate configuration endpoint was added. `requiresExpiry=false` remains NOT_APPLICABLE in F03 even if a threshold is configured. Inventory quantities are unchanged by threshold updates.

F03 uses only this Product threshold: no Store fallback. The legacy Store expiry-window endpoint is deprecated. New E is binary from the earliest-expiring ACTIVE positive-quantity batch with expiry strictly after the analysis date. *(Superseded 2026-11-24: a batch expiring today IS sellable; see the top of this file.)* `GET /api/utility/expiry-push-batches` provides a Store Admin/Merchandiser current push view independently of mining; see the F03 contract.


Contract checked against the running OpenAPI export, F02 ERD and current Backend source on 2026-11-19. Every route requires a bearer JWT. Resources are scoped to the authenticated Store; request bodies cannot choose a Store. Cross-Store product/category/batch access is returned as 404. F02 soft-deletes Products only (`DELETE /api/products/{id}`, 2026-11-24; there is no restore), does not delete Categories and does not expose stock-movement APIs; batch DELETE routes only clear optional dates.

## DTOs

- `CategoryRequest`: required nonblank `name:string` max150 and `status:string` in `ACTIVE|INACTIVE`.
- `CategoryView`: `{id:int32,name:string,status:string}`.
- `ProductRequest`: required `name:string` max180, `unit:string` max40, `requiresExpiry:boolean`, `sellingPrice:number >= 0`, `costPrice:number >= 0`, `status:ACTIVE|INACTIVE`; nullable/optional `categoryId:int32` and optional `confirmSimilarName:boolean`. Do not send `sku`, an ID, Store ID, stock or F03 score fields.
- `ProductView`: `{id:int32,sku:string,name:string,unit:string,requiresExpiry:boolean,category:CategoryView|null,sellingPrice:number,costPrice:number,status:string,stockQuantity:int64}`. `id` and `sku` are generated/read-only; `stockQuantity` is derived from all batch remaining quantities and read-only.
- `ProductPage`: `{content:ProductView[],page:int32,pageSize:int32,totalElements:int64,totalPages:int32}`.
- `BatchCreateRequest`: required `receivedAt:string` ISO date-time and `initialQuantity:int32 > 0`; nullable/optional `expiryDate:string` ISO date and `pushDay:string` ISO date. Do not send `batchCode` or an ID. Expiry required if Product `requiresExpiry=true`.
- `BatchPatchRequest`: optional `remainingQuantity:int32 >= 0`, `status:ACTIVE|BLOCKED`, `pushDay`, and `expiryDate`; at least one non-null field must be supplied. Remaining may not exceed initial quantity. Null/omitted date fields mean unchanged; use DELETE routes to clear them.
- `BatchView`: `{id:int32,productId:int32,batchCode:string,receivedAt:date-time,expiryDate:date|null,initialQuantity:int32,remainingQuantity:int32,status:"ACTIVE"|"BLOCKED",createdAt:date-time,updatedAt:date-time,pushDay:date|null,effectiveStatus:"ACTIVE"|"BLOCKED"|"EXPIRED",daysToExpiry:int32|null,warnings:("MISSING_PUSH_DAY")[]}`. ID and `batchCode` are backend-generated/read-only. New batches start `remainingQuantity=initialQuantity`, `status=ACTIVE`. `effectiveStatus`, `daysToExpiry` and `warnings` are computed on read in the Store time zone and are never writable; `status` is the stored value.
- `InventorySummary`: `{productId:int32,totalQuantity:int64,sellableQuantity:int64,expiredQuantity:int64,blockedQuantity:int64,expiringSoonQuantity:int64,batchesMissingPushDay:int64}`.

Product list query parameters: `search` default empty; `categoryId` optional int32; `status` default empty (`ACTIVE|INACTIVE` when nonempty); `page` default0, >=0; `pageSize` default20, 1..100; `sortBy` default `name`, supported `name|sku|category|unit|costPrice|sellingPrice|status|requiresExpiry|stockQuantity`; `sortDirection` default `asc`, supported `asc|desc`. Search matches name or SKU without case sensitivity. Invalid sort gives 400. Ties use `productId ASC`, regardless of requested direction, to keep pagination stable. Page is zero-based. Unlike category and batch lists, product list returns pagination metadata in `ProductPage`.

SKU is backend-generated for new Products from their database Product ID and remains unchanged on Product update. The database Store-scoped SKU constraint remains in place. An exact product name, or a one-character edit when the normalized names are at least four characters, in the same Store is not a uniqueness violation: create/update returns a `409 PRODUCT_NAME_CONFIRMATION_REQUIRED` warning until the client retries with `confirmSimilarName:true`. Category names have no uniqueness constraint in the current migration. A Product category is checked for Store ownership, but the service does not require that Category status is ACTIVE. Product status and category status are `ACTIVE|INACTIVE`; batch status is `ACTIVE|BLOCKED`. Category update is a full request replacement; Product PUT also requires the full `ProductRequest` body.

## Inventory rules

- `totalQuantity` sums every batch's remaining quantity, including blocked and expired stock. No batch yields zero.
- *(2026-11-24, DEC-20261124-01)* **Expired = today is after `expiryDate`** (Store-local `Asia/Ho_Chi_Minh`); a batch expiring today is still active. **EXPIRED wins over BLOCKED.**
- `expiredQuantity` sums batches with a non-null expiry date before today, **whatever their stored status**.
- `blockedQuantity` sums stored BLOCKED batches that are **not** expired.
- `sellableQuantity` sums stored ACTIVE batches with no expiry date or an expiry date on or after today.
- `expiringSoonQuantity` sums stored ACTIVE batches with `today <= expiryDate <= today + expiringWithinDays` (both ends inclusive). It is part of sellable quantity and is not an additional disjoint bucket.
- `batchesMissingPushDay` counts batches of an expiry-tracked product with no push day that are not expired (the `MISSING_PUSH_DAY` warnings); it is 0 for a product with `requiresExpiry=false`.
- Expired, blocked and sellable quantities do not overlap.
- Time zone defaults to `Asia/Ho_Chi_Minh` (`paspm.store-time-zone`), configured at application level in current source, not per-Store.
- Summary SQL does not check Product status, so a deactivated Product's batches can still be counted as sellable by this summary. The frontend should display Product status separately.
- Batch quantity constraints: initial >0; remaining >=0 and <=initial. Receive sets remaining equal to initial. PATCH cannot change `batchCode`, `receivedAt`, or `initialQuantity`. `expiryDate` can be set by PATCH; JSON null/omission retains the date. `DELETE /api/inventory-batches/{id}/expiry-date` clears it only when the Product does not require expiry. `pushDay` must be on or before `expiryDate` when both are set. There is no adjustment history/stock-movement endpoint.
- Generated batch codes use the Store-local calendar date represented by `receivedAt` and a per-Product sequence that continues across dates (minimum three digits); the database uniqueness constraint remains the final safeguard. Older existing codes do not change.

## F02 / F03 ownership

F02 Product create/update owns `requiresExpiry`, generated SKU, category, unit, prices, and Product status. SKU is generated at create and read-only afterwards. F02 batch APIs own batch expiry, push day and quantities. `stockQuantity` is derived and cannot be edited. The F03 API owns `stock_priority_score` and `seasonal_priority_score` through `/api/utility/products/{productId}/scores`; ProductRequest does not accept these fields. F03 derives expiry priority using inventory batches and a fixed analysis date. Do not add F03 score fields to F02 Product forms/contracts.

## Product soft delete (2026-11-24, DEC-20261124-03)

`DELETE /api/products/{id}` — `STORE_ADMIN` of the owning Store only. Cross-Store, unknown and already-deleted ids are 404 (after the role check). There is no restore endpoint.

409 body (`code` is machine-readable; show `reason` to the user):

```json
{"code":"PRODUCT_HAS_SELLABLE_STOCK","error":"Product cannot be deleted","reason":"The product still has 7 sellable unit(s) (ACTIVE, not expired); sell, write off or block them first, and remove it from the live campaign(s)","sellableQuantity":7,"campaigns":[{"campaignId":12,"status":"ACTIVE"}]}
```

| `code` | Meaning | `sellableQuantity` | `campaigns` |
|---|---|---|---|
| `PRODUCT_HAS_SELLABLE_STOCK` | stored ACTIVE batches with remaining > 0 and not expired hold units (a batch expiring today counts); expired, BLOCKED and empty batches do not block. Wins when both reasons apply | > 0 | live campaigns, possibly empty |
| `PRODUCT_IN_LIVE_CAMPAIGN` | placed in layout A or B of a PUBLISHED or ACTIVE campaign (DRAFT/ENDED do not block) | 0 | one or more `{campaignId, status: "PUBLISHED"|"ACTIVE"}` |

After a successful delete: the row, its SKU, batches and every historical reference stay in the database; `status` becomes `INACTIVE`; the product is excluded from `GET /api/products` **before pagination** (`totalElements`, `totalPages` and the page contents ignore it), from the similar-name check and from every product/batch/summary route (404). The SKU is never reused. Seasons keep the assignment (`SeasonProduct.deleted: true`); a new season assignment is `409 PRODUCT_DELETED`. F04 still resolves its SKU and adds a `PRODUCT_DELETED` warning to each imported row of it ([F04 contract](F04_TRANSACTION_API.md)).

Handled validation response:

```json
{"error":"Invalid request fields"}
```

A more specific service validation may return e.g. `{"error":"Remaining quantity cannot exceed initial quantity"}`. Missing/foreign Store resources are reported as 404.

## Verification status and ERD differences

All 17 F02 method/path operations appear in the runtime OpenAPI document. `CatalogIntegrationTest` exercises authentication/role denial, category/product CRUD/status, Store isolation, batch CRUD, required expiry, quantity/status/date patch and date clearing. The OpenAPI document is generated from the runtime endpoint; no interactive Swagger UI session was run for this update.

OpenAPI does not encode nullable response fields: `ProductView.category` can be null when no category is assigned and `BatchView.expiryDate` can be null for a non-expiring Product, although its schema shows nonnullable object/date types. Treat these as nullable in TypeScript. The ERD labels the account table `USER`; the implemented schema uses `app_user` to avoid reserved-word issues. The ERD uses `CATEGORY` / `PRODUCT` / `INVENTORY_BATCH`, and migrations V1/V3 implement these entities, including Store-scoped unique SKU, composite Store/category ownership, and unique `(product_id,batch_code)`. No stored Product stock column exists. F03 migration V4 adds score columns separately; this is consistent with field ownership in the F03 utility API.

## Historical: 2026-11-15 — Batch push day (F03 Weight v2, Q1/P5)

- `BatchCreateRequest` adds optional `pushDay` (ISO date). `BatchPatchRequest` adds optional `pushDay`; it counts toward the "at least one field" rule, so `{"pushDay":"2026-12-01"}` alone is valid. `BatchView` returns `pushDay` (date or null).
- `pushDay` must be on or before `expiryDate` → otherwise 400 (also a database CHECK). PATCH cannot clear a push day (null means "not provided").
- Roles unchanged: Store Admin only for batch writes (Merchandiser 403); foreign batch → 404.
- `ProductRequest.expiryPushDays` / `ProductView.expiryPushDays` are **deprecated** (P5): still accepted, validated (≥ 0) and stored, but ignored by every calculation. F03 W2 uses `inventory_batch.push_day`.
- No backfill: existing batches have `pushDay = null` until the Store Admin sets it; F03 only warns (`MISSING_PUSH_DAY`). Tests: `PushDayIntegrationTest`.

## 2026-11-16 — Clear a batch push day (additive)
`DELETE /api/inventory-batches/{id}/push-day`: Bearer authentication, STORE_ADMIN only, caller's Store. No body. Returns HTTP 200 and the same `BatchView` as GET/PATCH with `pushDay: null`. Repeating on an already-clear batch succeeds without updating its timestamp. Unknown/foreign batch 404, wrong role 403, unauthenticated 401. Persisted quantity, status and expiry are unchanged. PATCH absent/null `pushDay` retains its value; only DELETE clears it. Future calculations report `MISSING_PUSH_DAY` for otherwise eligible batches.

## 2026-11-16 — `expiryPushDays` removed (DEC-20261116-02, V26)

- `ProductRequest` (create `POST /api/products`, full update `PUT /api/products/{id}`) no longer has `expiryPushDays`. The backend rejects unknown JSON fields, so a request that still sends it — any value, including `null` — gets **400** and nothing is written.
- `ProductView` (list, detail, create/update responses) no longer contains `expiryPushDays`.
- The JPA entity no longer maps the column, and migration V26 drops `product.expiry_push_days` together with `product.stock_priority_score` and `product.seasonal_priority_score` (and their CHECK constraints). Not reversible without a backup taken before V26.
- Use the batch `pushDay` (create, PATCH, `DELETE /api/inventory-batches/{id}/push-day`). Roles unchanged.
- Tests: `LegacyProductFieldsRemovedTest`, `LegacyProductColumnsV26MigrationTest` (H2 + MySQL), `PushDayIntegrationTest.productExpiryPushDaysIsRejectedAndScoringUsesBatchPushDays`.
