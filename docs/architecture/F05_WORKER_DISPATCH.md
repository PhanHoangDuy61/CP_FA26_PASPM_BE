# F05 worker dispatch — implementation under verification

Status: **NOT_READY for release**. This describes the current branch, not an approved production-readiness claim. Scheduled mining is implemented on the Scheduler branch (see the final section) but stays off unless an instance sets `paspm.mining.schedule-dispatch-enabled=true`; where it is off the activation API returns 503.

Each Backend process assigns itself a random owner UUID. A one-second database poll finds PENDING requests and RUNNING requests with an owned, expired lease; the bounded local queue is only a wake-up hint. Queue rejection leaves the database record eligible for a later poll. A worker must atomically claim a Store/request lease with a monotonically increasing fencing token before execution. V16 provides the lease fields (formerly V15; renumbered after F04 took V12). Unowned historical RUNNING records are deliberately not presumed abandoned and require separate investigation; PENDING historical requests remain eligible without changing their saved configuration or frozen input.

The lease lasts 30 seconds and is renewed every five seconds using the database clock. If renewal fails or ownership is lost, the worker interrupts its execution thread; the SPMF engine attempts to terminate its child process. Lease expiry and reclaim can result in more than one physical process executing; only fenced persistence is intended to prevent stale writes. Shutdown interrupts local workers and leaves claimed requests for expiry and recovery.

Repository methods for resetting/claiming runs, writing patterns and benchmark fields, and failing runs require a claim. They lock and verify Store, request, owner, fence and unexpired lease in a short transaction, including a second check before commit. No row lock is held during SPMF. Request finalization verifies the same ownership. A reclaimed request resets only RUNNING runs; COMPLETED runs and their already committed patterns remain untouched, while output and completion for a run commit together. Database failures in persistence leave the lease to expire instead of marking the run as a successful result. Polling retries naturally on the next interval; lease-acquisition/renewal errors are logged without secrets.

Historical note: this paragraph originally recorded the state before the independent-JVM and subsequent container tests. Later sections and the current acceptance matrix supersede it. Unowned legacy RUNNING requests still require manual investigation, and the tests do not establish exactly-once physical execution.

## Multi-JVM verification — 2026-11-01

The preceding paragraph is historical. The subsequent opt-in test launched independent Java 17 Backends using the same disposable MySQL 8.4 schema and real SPMF Java 25. It verified healthy ownership across a second startup, multiple heartbeat intervals, a simulated renewal rejection, expiry and reclamation, actual stale repository-write rejection, SIGKILL recovery, post-commit/pre-enqueue recovery and queue saturation. Detailed actual evidence is in `docs/testing/evidence/F05_MULTIJVM_FINAL.txt` and `README_F05_MULTIJVM.md`. Tests use barriers compiled only into the test classpath; production worker and API logic remain real.

**P0-1 remains OPEN as a production-safety gate.** During a separate test the actual SPMF child was paused while running, the owning Backend received SIGKILL, and the Java 25 child remained alive. The test explicitly killed that orphan; another Backend recovered the request with a higher fence and persisted one valid output. `SpmfMiningEngine.execute()` destroys the child in `finally` during normal exception/shutdown handling, but the JVM cannot execute `finally` after SIGKILL. An external process supervisor or platform-supported parent-death strategy requires design and verification before claiming automatic cleanup; none was implemented. This observation does not imply that the orphan can bypass database fencing.

**P0-2 is RESOLVED for new eligible committed requests in the tested flow**, subject to the recorded environment and fault coverage: real administrative requests were recovered after killing the sender between commit and enqueue, and 11 requests survived queue saturation and worker death. A separate real-API test killed the Backend while its transaction was blocked before commit and confirmed zero committed requests. Historical RUNNING rows with null ownership are intentionally excluded from automatic reclaim and still need an operational reconciliation procedure. Scheduler activation remains 503 and scheduler work is separate.

## Orphan cleanup continuation — 2026-11-01

**P0-1 OPEN; no new cleanup mechanism is implemented or verified.** The observed Java 25 child survived SIGKILL of the Java 17 Backend, so the current `SpmfMiningEngine.execute()` finally block does not provide a parent-death guarantee. No process should be terminated based solely on a stored PID. The existing engine does not persist the requested child identity, fencing token and process start-time metadata, so it does not yet satisfy the proposed recovery/cleanup requirements.

The checked workstation reports macOS Darwin arm64. `compose.yml` defines MySQL and mail services, not a Backend container or production process supervisor. Project local setup describes Linux and macOS but the target deployment OS, container lifecycle and permissions have not been established. Docker CLI is installed on this workstation, but its daemon was unavailable during this inspection. No assertion is made about Linux deployment compatibility from the macOS test.

Candidate approaches remain conditional on the target: (1) Linux parent-death primitives or an externally managed per-job cgroup, with explicit startup-race, supervisor-death, PID identity and unsupported-platform handling; (2) a per-job independent supervisor with an independently enforced fail-safe deadline and verified process identity, tested for both Backend and supervisor death; or (3) deployment isolation whose supervisor kills the entire job scope. A process group or JVM shutdown hook alone is insufficient. None has been implemented or accepted as a fix, and a Linux-only solution cannot be certified from the present macOS host. Select and verify the mechanism against the actual runtime before enabling scheduling or claiming P0-1 complete.

For the separate historical-unowned-request issue, see `F05_LEGACY_RUNNING_RECONCILIATION.md`: a read-only inventory and per-request human-review process, with no automatic status changes. This does not assert that any target database was inspected or repaired.

## Linux Docker parent-death implementation — 2026-11-01

The preceding orphan-follow-up paragraph is historical. The selected target is Linux Docker; Windows and macOS remain local-development platforms. On Linux, the Backend starts `python3 -I` using an argument vector, without a shell. The small bootstrap calls `prctl(PR_SET_PDEATHSIG, SIGKILL)`, verifies the parent PID after setting it, rejects privileged/capability-bearing Java executables and then `execv`s the trusted Java executable. The Java process retains the same PID and kernel parent-death setting. If the Backend dies before bootstrap completes, the parent check prevents executing Java; if it dies afterwards, the kernel sends SIGKILL to the directly owned child. Both runtime probes and mining processes use the path. Python missing, unsupported `prctl`, denied metadata checks or nonzero preflight fails mining closed; no unsupervised Linux fallback is configured. No independent long-running watchdog is used.

This protection relies on a genuine unprivileged Java executable from a trusted, non-writable runtime, Python 3 with the standard `ctypes` module, and a container seccomp/security policy allowing the required `prctl` and executable metadata checks. Do not replace Java with a wrapper that forks or clears the kernel setting. The process association (Store, request, run, lease owner and fence, PID, process start time and outcome) is emitted to Backend logs; the database remains the authority for request recovery. Recovery does not signal processes by a stored numeric PID and does not require a PID table. Configure durable centralized logs if operational retention is required.

Linux process death and zombie reaping are separate responsibilities. In the tested configuration the kernel kills the SPMF process; a container init reaps terminated orphaned children when the Backend JVM is not PID 1. `--init` alone is not a parent-death mechanism and is not claimed to kill running children. A future Backend deployment must include a verified init/supervisor arrangement and all prerequisites; the current repository has no Backend Dockerfile. A force-killed Backend can leave temporary files because its Java `finally` cannot run; use a separately designed, identity-aware temp-file retention policy. While a launcher is stopped before it executes the `prctl` call, the kernel cannot enforce parent-death handling until that bootstrap runs; do not claim a guarantee against hostile suspension of that initialization window.

On handled interruption, the Backend requests termination, waits up to two seconds, then forces termination and waits up to five seconds. Windows and macOS preserve direct local-development execution with an explicit warning and have no Linux SIGKILL guarantee; do not deploy them as though they did. The existing V16 leases, fencing, durable dispatch and disabled scheduler remain unchanged. See the evidence guide for actual test results and deployment limitations.


## Scheduler continuation — 2026-11-01 (supersedes earlier scheduler descriptions)

Status **NOT_READY**. The internal dispatcher is disabled by default (`paspm.mining.schedule-dispatch-enabled=false`); the public enable operation still returns 503. Do not enable polling in a deployed environment until the required multi-container acceptance tests pass. The scheduler polls up to five due schedules and five occurrences every five seconds. V17 adds persisted occurrence owner, fence, expiry, attempt counter and retry time. An expired owned claim can be reclaimed; unowned historical PROCESSING rows are not automatically assumed abandoned.

`PENDING` is awaiting processing or retry; `PROCESSING` is claimed; `DISPATCHED` has an associated mining request; `COMPLETED` and `FAILED` are terminal. Snapshot creation and request linkage run in one fenced database transaction, separately from algorithm execution. Transient failures retry at most three total attempts, with 15/30 second delays; other errors become terminal. Reconciliation consults only terminal requests in the same Store. The existing worker's request lease/fence remains separate from the occurrence lease. An operation exceeding the 300-second occurrence lease rolls back; there is no occurrence-lease heartbeat.

The date window covers preceding complete calendar days. Monthly overflow, timezone/DST behavior, catch-up and retry limits are implementation policies pending Product Owner confirmation. Schedule timezone versus Store transaction-date timezone also needs explicit approval. Normal dispatch with two independent final-image containers has been exercised on a synthetic MySQL fixture. Crash/restart and failure recovery for the new occurrence pipeline have not yet been verified on those containers. The public schedule activation safeguard remains in place.

### Crash acceptance continuation — 2026-11-01

See [crash evidence](../testing/evidence/F05_SCHEDULER_CRASH_ACCEPTANCE_2026-11-01.txt) for two-container tests with deterministic database barriers, including reservation before/after commit, uncommitted snapshot preparation and request-link rollback, stale-owner resumption, a global mining configuration update during preparation, and a schedule-disable API request waiting for the in-flight transaction. In the crash-before-finalization experiment, MySQL completed an already-running autocommit statement after the JVM was killed; this was not a demonstration that the surviving instance reconciled it. The test-only database advanced occurrence lease/backoff times to exercise selected recoveries; natural timeout and all other failure boundaries remain separate acceptance items.

Snapshot and request writes and their occurrence links currently participate in the outer `MiningOccurrenceProcessor.process` transaction. There is no independent scheduled-path commit between snapshot creation and linking, or between request creation and linking. An `AFTER UPDATE` barrier verified rollback after the request link statement and before outer commit. The observed state machine remains `PENDING → PROCESSING → DISPATCHED → COMPLETED|FAILED`, with bounded retry back to `PENDING`; request/run state and worker fencing remain separate. Public activation remains 503 and the policy decisions in [the PO register](../reports/F05_SCHEDULER_POLICY_DECISIONS.md) are pending.

A later finalization-specific rerun combined a blocked UPDATE, test-only termination of that MySQL connection and SIGKILL of A. The surviving B instance reconciled the existing DISPATCHED occurrence after its already-COMPLETED request; the same snapshot and request IDs were retained. The separate connection-kill injection is part of the evidence and should not be omitted when interpreting the result.

### Final-gap verification — DEBUG rejection event

When a local executor rejects enqueue because its bounded queue is full, `MiningWorker` emits `MINING_QUEUE_REJECTED store=<id> request=<id>` at DEBUG and removes the local queued marker; the database record remains the source of truth for subsequent polling. Do not enable DEBUG indefinitely without an operational log-volume and retention policy: repeated polls can emit repeated events. The event intentionally includes identifiers but no JWT, credentials, payload or paths. [Final-gap evidence](../testing/evidence/F05_FINAL_GAPS_2026-11-01.txt) records actual two-container rejections and redispatch, forced TCP disconnection/reconnection, simultaneous startup, natural retry exhaustion and SPMF isolation/startup race. These results do not approve PO policies or remove the 503 guard.

## Scheduler state after the D1–D10 confirmations — 2026-11-02 (Scheduler branch; supersedes the paragraphs above where they differ)

Status: `IMPLEMENTED`, `LOCAL_VERIFIED`, `CI_NOT_RUN`, `RELEASE_SIGNOFF_PENDING`. Register: [PO_DECISION_REGISTER_F05_2026-11-01.md](../decisions/PO_DECISION_REGISTER_F05_2026-11-01.md).

**Gate.** One flag, `paspm.mining.schedule-dispatch-enabled` (default `false`), controls (a) whether `PUT /api/system/mining/schedules/{id}` may set `enabled=true` (otherwise 503 before any write), (b) whether the dispatcher thread starts (poll every 5 s), and (c) the startup zone guard: with the flag on, `paspm.store-time-zone` must be `Asia/Ho_Chi_Minh`. In a multi-instance deployment set it identically on every instance behind the API.

**Reservation (one transaction, schedule row `FOR UPDATE`, READ_COMMITTED).** Only enabled schedules whose zone equals the Store zone and whose lookback is 7–365 are due. For a due schedule the code walks the recurrence from the stored cursor: every fire time that is followed by another fire time ≤ now is inserted as `SKIPPED` (`skip_reason = MISSED_SUPERSEDED_BY_LATER_OCCURRENCE`; no actor, range, snapshot or request); the last one is inserted `PENDING` with the frozen schedule version, config version, window and the **scheduler principal** as actor; the cursor moves past it. At most 500 skips are written per transaction; a longer backlog resumes on the next call with the cursor already advanced. The unique key `(schedule_id, scheduled_at)` and the deterministic request key `PASPM-SCHEDULE-V1|schedule|instant` make every logical fire time exist once even with several instances. The method `reserve` returns the reserved occurrence id and the number of skips; `reserveOne` remains for callers that need only the id.

**Preparation (unchanged transaction shape).** `PENDING`/expired-`PROCESSING` occurrences with fewer than 3 attempts are claimed with a fenced lease (300 s). `MiningOccurrenceProcessor` runs the fresh F03 snapshot and the Mining Request in one REPEATABLE_READ transaction; it requires that the occurrence actor is the scheduler principal, that the occurrence zone equals the Store zone and, until the request exists, that the schedule is still enabled and unchanged (otherwise `FAILED/HTTP_409`). Once the request exists, a replay only re-links it and never re-checks the schedule. A failure rolls the snapshot back (no orphan; verified with `kill -9` inside the transaction).

**Failure handling.** Retryable (5xx or transient database error): back to `PENDING`, `failure_code = RETRYABLE_FAILURE`, `failure_message`, `next_retry_at` +15 s after attempt 1 and +30 s after attempt 2; the third failure is `FAILED/RETRY_EXHAUSTED` with the cause. Non-retryable: `FAILED/HTTP_<status>` with the message at once. A lease that expires after the last attempt is `FAILED/RETRY_EXHAUSTED`. `reconcile()` copies a terminal request's status to the occurrence and, for a failed request, the first failed run's message.

**Not built, by decision:** cancel on disable (a reserved but unprepared occurrence fails with `HTTP_409`, a committed request finishes), a maximum catch-up age, any external notification.
