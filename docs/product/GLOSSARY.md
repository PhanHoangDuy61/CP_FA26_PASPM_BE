## 1. Organisation, roles and scope

| Term | Definition |
|---|---|
| **Store** | One retail store, and the unit of data isolation. Every store-bound record carries `store_id`. The API takes a user's Store from the authenticated account (the JWT identifies the user; there is no Store claim), never from the request body. Profile: `name` (unique ignoring case), `slug`, `address`, `phone`, icon and banner; `status` ACTIVE/INACTIVE and `version` (DEC-20261123-01). |
| **Store status** | `ACTIVE` or `INACTIVE`. A System Admin deactivates or reactivates a Store; it is never deleted. INACTIVE: its users get 403 `STORE_INACTIVE` (one central guard), no new System Admin work or user assignment (409), schedulers skip it, in-flight work finishes, history stays readable, public images are not served. |
| **Store branding image** | The Store icon (≤ 1 MiB) or banner (≤ 5 MiB), PNG or JPEG, ≤ 4000×4000 px. The database keeps a relative storage key (`stores/{storeId}/{uuid}.png`), never a URL or BLOB; the API builds the URL. |
| **MediaStorage** | Shared storage abstraction for uploaded images (`common.media`); local filesystem under `PASPM_MEDIA_ROOT` today, replaceable by object storage. Avatars use it too. |
| **Store isolation** | Users only see their own Store's data. A record that belongs to another Store answers **404** (not 403), so its existence is not revealed. In the database, composite foreign keys `(store_id, id)` stop a record from referencing another Store's record. |
| **SYSTEM_ADMIN** (System Administrator) | Platform-level role with no Store. Manages accounts and roles, sets **λmax**, owns the mining configuration (minUtil) and schedules, and can submit mining for a selected Store. It can read a Store's snapshots, requests and runs, but not raw patterns. |
| **STORE_ADMIN** (Store Admin / Operations Manager) | Store role. Manages categories, products, prices, costs, inventory batches and **push days**, and imports transactions. **Activates, ends and rolls back** campaigns. |
| **MERCHANDISER** (Retail Planner) | Store role. Sets λ, α, β and N, manages seasons, creates utility snapshots and submits mining for its own Store. Generates and reviews recommendations, edits layout B, simulates, decides on and publishes campaigns. |
| **END_CUSTOMER** | Shopper account with no Store, created by email OTP or Google sign-in. F10 needs it for the cart. F09 viewing is planned to be anonymous. |
| **SYSTEM_SCHEDULER** | Internal machine principal used by the scheduled-mining dispatcher. Nobody can log in as it. |
| **Owner decision / DEC-yyyymmdd-nn** | A business decision recorded in `docs/decisions/`. Decisions override older report text. |
| **Record of changes (ROC)** | Dated change notes for teammates in `docs/record-of-changes/`. |

## 2. Catalogue, inventory and transactions (F02, F04)

| Term | Definition |
|---|---|
| **Product** | A sellable item of a Store, with SKU (generated by the backend as `SKU-` + the 11-digit product ID, read-only, unique per Store, DEC-20261119-07; older databases keep their earlier SKUs such as `FOODMART-xxxx`), name, unit, category, selling price, cost price, status and whether it requires an expiry date. Since V26 it no longer stores stock, priority scores or `expiryPushDays`. Since V28 it can be **soft-deleted** (`deleted_at`, `deleted_by`, status INACTIVE): the row, SKU and history stay, and catalogue queries exclude it. |
| **Soft delete (product)** | `DELETE /api/products/{id}` by the Store Admin of the owning Store. 409 `PRODUCT_HAS_SELLABLE_STOCK` or `PRODUCT_IN_LIVE_CAMPAIGN` while the product still has sellable stock or sits in a PUBLISHED / ACTIVE campaign layout. No restore; the SKU is never reused. |
| **Category** | A product group within a Store, either ACTIVE or INACTIVE. |
| **Inventory batch** | One received lot of a product, with a backend-generated code `BATCH-YYYYMMDD-NNN`, quantity, remaining quantity, expiry date, **push day** and stored status (ACTIVE / BLOCKED). The API adds the computed `effectiveStatus`, `daysToExpiry` and `warnings`. |
| **Expired batch / `effectiveStatus`** | A batch is expired only when today (`Asia/Ho_Chi_Minh`) is **after** its expiry date, so it is still active on the expiry date. Never stored: `effectiveStatus` is `ACTIVE`, `BLOCKED` or `EXPIRED` (EXPIRED wins over BLOCKED), and `daysToExpiry` is 0 on the expiry date. "Expiring soon" = not EXPIRED and `0 ≤ daysToExpiry ≤ 7`. |
| **Similar-name confirmation** | F02 check: a product name equal to, or one character away from, another product's normalized name in the Store (4+ characters) returns 409 `PRODUCT_NAME_CONFIRMATION_REQUIRED`; the client retries with `confirmSimilarName: true`. Names are not unique. |
| **Sellable stock** | Stock is never stored on the product. It is the sum of remaining quantity over ACTIVE batches with remaining > 0 whose expiry date, if they have one, is **on or after** today in Store-local time, so a batch that expires today is still sellable (changed 2026-11-24, DEC-20261124-01; it was "strictly after today"). For a product that requires expiry, a batch with no expiry date is not counted, and F06 reports `NEEDS_RECHECK`. |
| **Push day** (`push_day`) | The date by which the Store Admin wants a batch sold. It must be on or before the expiry date. It drives U_expiry. If it is missing, the result is a `MISSING_PUSH_DAY` warning, the batch is excluded from U_expiry, and nothing is backfilled (there is no default such as `expiry − 7`). The batch API also returns the `MISSING_PUSH_DAY` warning for expiry-tracked, non-expired batches whatever their stored status. It can be cleared with `DELETE /api/inventory-batches/{id}/push-day`. |
| **FEFO** | First-Expired-First-Out ordering. In Weight v2 it orders by push day ascending, then batch id. |
| **Sales transaction** | An imported order with a source order id, time, status and content hash. Its lines are **transaction items** (product, quantity, unit price, unit cost). |
| **Eligible transaction (F03-eligible)** | A `COMPLETED` order where every line has unit price ≥ unit cost. Only these feed utility profiling and offline simulation. |
| **Import batch / staging row** | One file import, plus one stored raw row per CSV line with its validation status. Async imports move through the stage `RECEIVING → QUEUED → IMPORTING → COMPLETED / COMPLETED_WITH_ERRORS / FAILED`. The batch status uses `PROCESSING` where the stage says `IMPORTING`, and old rows have stage `LEGACY`. |
| **Duplicate / Conflict** | Same order id with the same normalised content gives a *duplicate*, which is ignored. Same order id with different content gives a *conflict*, which is rejected and leaves history unchanged. |

## 3. Utility profiling — Weight v2 (F03)

| Term | Definition |
|---|---|
| **Base utility** | `quantity × (unit price − unit cost)` for one transaction line, at scale 6 with HALF_UP rounding. FoodMart data uses its original utility values. |
| **W(i)**, the product weight | `W = 1 + λ·(α·U_expiry + β·M)`, rounded half-up to 2 decimals, so `1 ≤ W ≤ round(1+λ, 2)`. |
| **Weighted utility** | `BaseUtility × W(i)`, at scale 6. This is a priority score, **not revenue or profit**. |
| **λ (lambda)** | Impact strength, chosen by the Merchandiser within `[0, λmax]`. |
| **λmax** | The upper bound of λ, and the only λ setting the System Admin controls. Default is 0.5. If λmax is lowered below a stored λ, the stored value is not clamped. It is reported as `lambdaValid=false`, and new snapshots get 409. |
| **α, β** | Weights of expiry risk and season, each in [0,1], with α + β = 1. Set by the Merchandiser. |
| **U_expiry(i)** (expiry risk) | `Q_risk / Q_eligible`, in [0,1]. It is the share of eligible stock that is not expected to sell by its batch push days at the current sales rate, simulated in FEFO order. A push day on or before the analysis date counts the whole remaining batch as risk. |
| **Q_eligible / Q_risk** | Q_eligible is the remaining units of eligible batches: ACTIVE, remaining > 0, not expired, with a push day. Q_risk is the part of those units expected to be unsold at the push day. |
| **v(i)** (sales rate) | Units sold in COMPLETED, eligible transactions over the last **N** days, up to and including the analysis date, divided by N. |
| **N** (sales window) | Days used for v. Default 30, range 1–365, editable by the Merchandiser. |
| **SLOW_MOVING** | Status when v = 0. It forces U_expiry = 0 and adds the warning `SLOW_MOVING_NO_RECENT_SALES`. |
| **Season** | A Store-scoped period with a name unique per Store, start date ≤ end date, weight in [0,1] and a version. The Merchandiser creates, updates, deletes and assigns it to products. A season that still has products assigned cannot be deleted (409). |
| **Active season** | A season whose `[start, end]` contains the analysis date, inclusive. |
| **M(i)** (seasonal score) | The highest weight among the active seasons assigned to the product, or 0 if none. |
| **Priority product** | A product with **W > 1** in the frozen snapshot. Decided 2026-11-17 and used by `priorityCoverage`. |
| **Analysis date / asOfDate** | The date the weights are computed for, usually the snapshot range end. |
| **Utility matrix** | One row per (transaction, product) of a date range, holding base utility, scores, W and weighted utility. |
| **Utility snapshot** | An **immutable** frozen utility matrix for a date range. It also stores λ, α, β, N, λmax, the active seasons (copied by value), U_expiry, M, W, warnings and source/matrix hashes. Status `READY`; the schema allows `FAILED`. Mining and recommendations always read a snapshot, never live data. |
| **scoringVersion** | The version tag inside frozen JSON. The current tag is `W2_EXPIRY_SEASON_V1`. Readers dispatch by this tag. Old JSON is never rewritten and unknown versions are rejected (`UNSUPPORTED_SCORING_VERSION`, 409, by the F03 and F06 readers). |
| *(legacy)* S, E, γ, stock priority score, expiry-push days, expiry window, `[λmin, λmax]` | The Weight model before 2026-11-15. It survives only in frozen historical JSON. The columns were dropped by V26, and the routes return 404 or 405. |

## 4. Mining (F05)

| Term | Definition |
|---|---|
| **HUI / HUIM** | High-Utility Itemset (Mining): sets of products whose total utility reaches **minUtil**. |
| **minUtil** | Minimum utility threshold, set by the System Admin as a **percentage** of total utility or an **absolute** value. It is converted once into the scaled integer domain. |
| **EFIM** | The HUIM algorithm used by PASPM, run from SPMF 2.67a. **Mining is EFIM-only** since 2026-11-16. |
| *(legacy)* **HUI-Miner, compare mode, benchmark** | Two-algorithm comparison and benchmark routes, removed 2026-11-16. Old requests may still show `HUI_MINER`, `COMPARING` and `comparisonStatus`. |
| **SPMF** | The Java pattern-mining library, version 2.67a, pinned by SHA-256. It runs in a separate **Java 25 child process** because the backend runs on Java 17. |
| **Transaction utility (TU)** | Sum of the weighted utility of one transaction. |
| **TWU** | Transaction-Weighted Utility of a product, meaning the sum of the TU of the transactions that contain it. |
| **Scale-6 / GCD conversion** | Lossless conversion of decimal utilities into SPMF integers: multiply by 10⁶, then divide by the GCD. |
| **EFIM-aware int32 guard** | SPMF uses signed 32-bit integers. Each transaction's utility, each product's TWU and the converted minUtil must all be ≤ 2,147,483,647, or the request gets 400. Totals use int64; `totalScaledUtility` is int64. Since 2026-11-19 (DEC-20261119-05), when a bound is exceeded the input is rebuilt with each item rounded to 1 đồng HALF_UP and checked again (see **Conversion mode**). |
| **Conversion mode** | How a mining request's SPMF input was built: `LOSSLESS` (scale-6/GCD, `F03_SCALE6_GCD_INT32_DENSE_V1`) or `WHOLE_UNIT_HALF_UP` (1 đồng, `F03_WHOLE_UNIT_HALF_UP_INT32_DENSE_V1`). It is frozen in the request; readers dispatch on `conversionVersion`. |
| **Mining configuration** | The global, **versioned** minUtil policy. A request keeps the version it was created with. |
| **Mining request** | A request to mine one READY snapshot of one Store, idempotent by `requestKey` (UUID). Status: `PENDING → RUNNING → COMPLETED / FAILED`. |
| **Mining run** | One algorithm execution for a request, with runtime, memory, itemset count and failure details. |
| **Progress stage** | `QUEUED → RUNNING → SAVING → COMPLETED / FAILED`. `LEGACY` marks old rows and `COMPARING` appears only on old requests. The percentage counts completed work. It is not an ETA. |
| **Pattern / itemset** | `high_utility_pattern` plus `pattern_item`: one discovered product set with its utility. |
| **OUTPUT_LIMIT** | Failure code when a run exceeds 2,000 patterns or 4 MiB of output. The fix is to raise minUtil. |
| **Lease / fencing token** | The worker claims a request with a time-limited lease and a fencing number. A crashed worker's request can be reclaimed, and stale writers are rejected. |
| **Mining schedule / occurrence** | A weekly or monthly schedule per Store, and each due time it produces. Older missed occurrences are recorded as `SKIPPED`. Preparation gets at most 3 attempts, then the occurrence is `FAILED` with `RETRY_EXHAUSTED`. **Enabling dispatch returns HTTP 503** until release sign-off. |

## 5. Recommendations (F06)

| Term | Definition |
|---|---|
| **Recommendation (candidate)** | A merchandising proposal derived from one completed mining run. It records type, products, utility, evidence, explanation, rule version and review status. |
| **BUNDLE** | 2 to `maxBundleSize` products (default 4) sold together. |
| **CROSS_SELL** | Anchor product plus suggested targets, created when confidence ≥ minConfidence (default 0.50). |
| **FBT** (Frequently Bought Together) | ≥ 2 products that pass both the support count (≥ 2) and the support ratio (≥ 0.05). |
| **BANNER** | Homepage highlight. It is the **only type that may contain a single product**. |
| **Support / support ratio / confidence** | Support is the number of frozen baskets that contain every product. Support ratio is support ÷ total transactions. Confidence is support ÷ anchor support. |
| **Rule version** | `F06_RULES_V1_1`. Policy changes never rewrite existing candidates. |
| **Review status** | `PENDING_REVIEW → APPROVED / REJECTED`. The Merchandiser decides once, with a reason. Approval publishes nothing and reserves nothing. |
| **Eligibility** | Live sellability check: `ELIGIBLE`, `NEEDS_RECHECK` or `INELIGIBLE`. |
| **readyForConsumption** | `true` only when the candidate is **APPROVED and currently ELIGIBLE**. Downstream features (F07–F10) must require `reviewStatus=APPROVED AND readyForConsumption=true` at the moment of use. |
| **inventoryChanged** | Product or batch metadata (or the date) changed since generation. It does not necessarily mean stock changed. |
| **seasonEnded / endedSeasons** | Warning that a season frozen in the snapshot has ended since. Nothing is re-run automatically. |
| **Expiry alert** | Push-day based alert of batches to clear. It does not depend on mining. |

## 6. Layout and campaign (F07, F08)

| Term | Definition |
|---|---|
| **Layout** | An ordered set of **placements**, also called blocks, in zones for the storefront homepage. Each placement is a whole approved recommendation. |
| **Zone** | Layout area mapped to a recommendation type: `BASELINE`, `BUNDLE`, `CROSS_SELL`, `FBT`, `BANNER`. Capacities come from the shared policy (`GET /api/layouts/policy`), with no invented defaults. Configured since 2026-11-19 (DEC-20261119-06): BANNER 3 blocks / 3 products, BUNDLE 4 / 16, CROSS_SELL 2 / 8, FBT 2 / 8, BASELINE 35 / 35. A capacity that is not configured is unbounded (`UNCONFIGURED_LIMITS_ARE_UNBOUNDED`). |
| **Layout A (baseline)** | Read-only layout built deterministically from the snapshot, ordered by how many transactions contain each product. It is a frequency baseline, not a utility ranking. Since 2026-11-19 it holds the top-K products only (K = 35, `F07_BASELINE_V2`); older V1 layouts hold every product. |
| **Equal-size comparison** | `OFFLINE_REPLAY_V2` compares B with the first N products of A, with N = distinct products in B, because the metrics and score grow with the number of products shown. F07 shows `equalSizeBaselineScore`. |
| **Layout B (proposed)** | Editable layout the Merchandiser builds per product. Each placement carries `zone`, `blockNo`, `position` and optional F06 `sourceRecommendationId`; manual source is `null`. A product may appear only once. Editing B never changes F06 evidence or Layout A. B must be `READY` before it can be selected. |
| **Layout revision** | Every edit creates a new revision. Reports pin exact revisions. |
| **Layout utility score** | "Weighted utility (snapshot)": the sum of `weighted_utility` of the distinct displayed products in the same snapshot. It is not revenue. |
| **Campaign** | A pairing of A and B for one snapshot, with lifecycle `DRAFT → PUBLISHED → ACTIVE → ENDED`. *Withdraw* moves PUBLISHED back to DRAFT. **Only an activated campaign changes the storefront.** A Store has at most one ACTIVE campaign. |
| **Decision** | The Merchandiser's choice of A or B, optionally backed by a report that matches the current revisions. |
| **Simulation report (offline replay)** | Immutable, `simulated:true`, `OFFLINE_REPLAY_V1`. It replays eligible transactions dated after the snapshot range and outside the snapshot. It is not a real-user A/B test and not a forecast. |
| **hitRate** | Evaluation transactions with ≥ 1 displayed product ÷ evaluation transactions. |
| **bundleConversion** | Evaluation transactions that contain every product of ≥ 1 saved `BUNDLE + blockNo` block in Layout B ÷ evaluation transactions. F06 provenance does not define the bundle. |
| **capturedUtility** | Base utility of purchased lines whose product is displayed ÷ base utility of all lines. |
| **priorityCoverage** | Agreed formula: priority products (W > 1) on the layout ÷ products on the layout, with W taken from the layout's frozen snapshot. Layout views measure the full layout. New offline reports measure the products compared on each side. |
| **Active layout projection** | `GET /api/storefront/active-layout` returns the layout of the active campaign, or `defaultLayout:true`. It is JWT-scoped for staff and is not the public storefront API. |
| **Rollback** | Store Admin action that restores the previously active campaign, or the default layout. |

## 7. Storefront, cart and analytics (F09–F11, planned)

| Term | Definition |
|---|---|
| **Storefront (F09)** | Public shop pages: homepage from the active layout, product detail and bundles. Anonymous read access through a separate public API (`/api/storefront/**`), for ACTIVE Stores only (DEC-20261125-04). |
| **storeSlug** | The Store `slug` (V27): unique, lowercase letters, digits and hyphens, set and changed only by a System Admin. The F09 public key of a Store. |
| **availability** | Planned per-product state such as `OUT_OF_STOCK`, recomputed when the response is built. |
| **Bundle cart (F10)** | Planned per-customer, per-Store cart. Adding a bundle adds all its items atomically after a recheck. No stock reservation, no order or payment, and no bundle discount. |
| **storefront_event** | Planned append-only event table (cart and bundle actions) that feeds F11. |
| **Retail Performance Dashboard (F11)** | Planned (MVP decided 2026-11-19), for Store Admin and Merchandiser: total weighted utility per snapshot, A/B simulation results (labelled simulated), bundle add-to-cart counts from `storefront_event`. No benchmark charts. |

## 8. Process and evidence

| Term | Definition |
|---|---|
| **NOT RUN / NOT_READY** | Labels for tests or features without execution evidence. Never report them as passing. |
| **Golden fixture** | Small dataset with independently computed expected results. |
| **FoodMart** | Public SPMF utility dataset (4,141 transactions, 1,559 products) used for training and tests. A test set is derived from it. |
| **Disposable database** | A throw-away MySQL instance or container for tests. Never test against a teammate's valuable local DB. |
| **Historical migration** | Flyway V1–V26 are frozen. Changes always go in a new version. |
