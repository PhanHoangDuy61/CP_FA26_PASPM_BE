# F05 Scheduler — proposed Product Owner decisions

Status for every row: **PENDING PRODUCT OWNER APPROVAL**. These proposals do not authorize activation or change the current implementation. Existing values below are implementation behavior, not evidence of approval.

| Policy | Proposal and rationale | Backend, API and database impact | Edge cases and current behavior |
| --- | --- | --- | --- |
| Transaction lookback | Store-targeted schedule supplies 1–3660 complete local calendar days, ending on the day before the occurrence; expose the selected range in history. This avoids a partly completed trading day. | Existing `lookbackDays`, frozen `range_start`/`range_end` and analysis date support this; communicate the range before activation. | New stores without sufficient history; empty eligible transactions; late imports; scheduled instant around local midnight. Current implementation already uses this range; approval pending. |
| Store timezone | Use the Store's approved IANA timezone as the single source for schedule and transaction-day boundaries; reject a mismatched schedule timezone. Asia/Ho_Chi_Minh may be a default only if the PO confirms its scope. | Needs a reliable Store timezone field/configuration and explicit API validation or derivation; historical occurrence zone remains immutable. Existing F04/F03 date-boundary behavior must be checked during implementation. | DST gaps and overlaps, moving a Store between zones and imports with offsets; an earlier approval of Asia/Ho_Chi_Minh for expiry does not automatically approve the scheduler policy. Currently schedule accepts its own IANA zone while transaction interpretation may use a different zone. |
| Weekly/monthly timing | System Admin selects a Store, local time, weekday or month-day; calculate future instants using the frozen IANA zone. Explain DST gap/overlap behavior in the UI. | Existing schedule DTO already has frequency, day, local time and timezone; recurrence and history should expose scheduled instant. | Avoid accidental repeated instants during fall-back; at DST gap move to the next valid local time, overlap use earlier offset. Current code implements these Java time rules; approval pending. |
| Monthly overflow | When the chosen day does not exist, run on the last day of that month. This retains one occurrence every month. | Existing recurrence already clamps with `min(day, month length)`; document in API and handoff. | Feb 29/30/31, leap years and next month recovery. Approval pending; alternative is skip the month. |
| Catch-up after downtime | Propose at most one most-recent missed occurrence per schedule after restart; older missed occurrences should be visible as skipped/auditable and not be silently executed as a backlog. This limits surprise resource usage. | Requires policy, durable audit representation and changes to reservation logic/schema or history; UI/API must show skipped windows. | Downtime across multiple weeks/months, simultaneous instances, re-enabling after a long pause, late imports. Current code reserves one occurrence per call, up to five per poll, and can continue processing an unbounded backlog across polls; proposal is NOT implemented. |
| Retry/backoff | Propose three total preparation attempts with 15 and 30 seconds backoff for transient failures, then a terminal failure visible in occurrence history; operators can investigate before a new explicit run. | Existing attempt count, lease, `nextRetryAt` and failure code support this, but production alerting and operator retry policy require definition. | Temporary MySQL/SPMF outage, application restart during delay, expired lease, permanent input validation failure, no retry after a request has failed. Current classification and limits require more fault testing and approval. |
| Configuration changes | Freeze the mining configuration version when reserving an occurrence and use it for all retries; changes apply to future reservations only, with no silent clamping. | Existing occurrence `config_version` and request link support this; verify retention and API display. Clarify separately whether disabling/editing a schedule cancels an already-reserved occurrence. | Config update concurrently with reservation, disabled or deleted actor, schedule edit after claim, retries after policy change. Current processing rejects changed/disabled schedule versions; decide whether that cancellation behavior is desired. |

The public enable API remains HTTP 503. Approval is required after the technical acceptance gates pass; these rows are a decision request, not a claim of acceptance.
