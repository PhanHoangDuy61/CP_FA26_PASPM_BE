## Implemented behavior

### Product and SKU

- Product IDs are generated by the database. Do not include an ID in a create request; treat IDs as read-only in the UI.
- The backend generates SKU on Product create as `SKU-` plus the database Product ID padded to 11 digits. For example, Product ID 42 produces `SKU-00000000042`. If that value already exists in the database from legacy data, generation checks and selects another 11-character code.
- `sku` is not part of `ProductRequest`. Clients must omit it from POST and PUT requests; sending it is an unsupported field and returns HTTP 400. `ProductView.sku` is read-only.
- Product update preserves its existing SKU. Existing Products retain their stored SKU; generation applies to newly created Products.
- Product IDs are globally generated, so newly generated SKUs are also unique across Stores. The existing Store-scoped database SKU constraint remains in place.
- Similar product names are a separate confirmation flow. An exact normalized name or one-character edit for normalized names of at least four characters returns HTTP 409 with `code: PRODUCT_NAME_CONFIRMATION_REQUIRED`. No write occurs on this response. After explicit user confirmation, retry with `confirmSimilarName: true`.
- Product sorting is allowlisted and supports `name`, `sku`, `category`, `unit`, `costPrice`, `sellingPrice`, `status`, `requiresExpiry`, and `stockQuantity`. Equal sort values use Product ID ascending as the stable tie-breaker.
- Product responses expose `requiresExpiry`; the UI should visibly distinguish products with and without expiry tracking. Put purchase cost before selling price in the form; this is a frontend presentation requirement, not a backend field-order change.

### Inventory batches

- Batch IDs are generated by the database and are read-only.
- Batch create does not accept `batchCode`. The backend generates `BATCH-YYYYMMDD-NNN` using the received date in the configured Store time zone, with a sequence scoped to the Product and padded to at least three digits. Concurrent creation for one Product is serialized using a Product row lock.
- `receivedAt` and `initialQuantity` are receipt facts and cannot be edited through PATCH. New batches start with `remainingQuantity = initialQuantity` and status `ACTIVE`.
- Batch PATCH supports remaining quantity, status, `pushDay`, and expiry-date correction. Remaining quantity must be between zero and initial quantity. Dates omitted or sent as JSON `null` are unchanged.
- `DELETE /api/inventory-batches/{id}/expiry-date` clears expiry only when the Product does not require expiry. Existing `DELETE .../push-day` behavior remains.
- Products requiring expiry must have an expiry date for each batch. A Product cannot be changed to require expiry while it has batches without expiry dates.

## API surface touched

- `GET /api/products`: allowlisted sorting described above; existing search, filters, and pagination remain.
- `POST /api/products`, `PUT /api/products/{id}`: backend-generated read-only SKU and similar-name confirmation flow.
- `POST /api/products/{id}/batches`: server-generated `batchCode`; do not send that field in the request.
- `PATCH /api/inventory-batches/{id}`: supports correcting expiry date in addition to existing editable batch fields.
- `DELETE /api/inventory-batches/{id}/expiry-date`: clear optional expiry date when permitted.

Store ownership continues to come from the authenticated principal, not the request body. Batch mutation remains `STORE_ADMIN` only. Product reads are available to `STORE_ADMIN` and `MERCHANDISER`; product writes remain `STORE_ADMIN` only.
