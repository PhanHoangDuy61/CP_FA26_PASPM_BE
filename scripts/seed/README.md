# Demo seed

`seed_demo.py` fills an **empty** PASPM database through the public REST API (the Store is created with `POST /api/system/stores`; direct SQL is only used for the final record counts). `seed.sh` loads `.env.seed` and runs it. Setup steps for the staging stack are in [STAGING.md §5](../../docs/setup/STAGING.md); the variables are listed in [.env.seed.example](.env.seed.example).

```bash
cp scripts/seed/.env.seed.example scripts/seed/.env.seed && chmod 600 scripts/seed/.env.seed
$EDITOR scripts/seed/.env.seed     # SEED_SYSADMIN_* must equal BOOTSTRAP_*; set SEED_ACCOUNT_PASSWORD
scripts/seed/seed.sh
```

## What the demo data contains

| Part | Created through | Content |
|---|---|---|
| Accounts | Admin invitation, self-registration (OTP read from Mailpit) | System Admin (bootstrap account), Store Admin, Merchandiser, End Customer |
| Catalogue | Store Admin API | 1 category, 1,559 FoodMart products named `FoodMart Item NNNN`; the backend generates their SKUs (`SKU-` + 11-digit product ID, DEC-20261119-07) |
| Inventory | Store Admin API | one batch per product (batch code generated by the backend, `BATCH-YYYYMMDD-NNN`); **551 products (35%) require expiry and carry an expiry date; 125 of them have no push day** |
| Transactions | Store Admin CSV import of the **import-ready copies** (below) | 4,776 orders, 19,932 lines, dated **2026-10-01 to 2026-10-04** (the last day ends at 06:00): 4,141 random FoodMart orders (`Part1`, `Part2`) plus 635 co-purchase orders (`Transactions_F04_Demo_Copurchase.csv`, [below](#co-purchase-baskets-why-the-demo-has-bundle-cross_sell-and-fbt-candidates)) |
| Seasons | Merchandiser API | 4 seasons, 1,451 product assignments (below) |
| Weight configuration | Merchandiser API | α = 0.6, β = 0.4, λ = 0.3, N = 30 days |

### FoodMart codes, server SKUs and the import-ready CSV copies

The dataset identifies products by **FoodMart codes** `FOODMART-NNNN` (`NNNN` = the SPMF FoodMart item ID, the same IDs as `paspm-experiments`). Since 2026-11-20 the backend generates every SKU and rejects a client `sku` (DEC-20261119-07), so the seed:

1. creates each product with the name `FoodMart Item NNNN` (and `confirmSimilarName: true`, because every FoodMart name is one character away from another), or finds it by that **exact name** on a rerun;
2. reads back the server SKU and writes **`mapping.csv`** (`foodmart_code,sku,product_id,name`);
3. writes **import-ready copies** of `Transactions_F04_Import_Test_Part1.csv`, `Part2.csv` and `Transactions_F04_Demo_Copurchase.csv` in which only the `sku` column is replaced through `mapping.csv` (CRLF and every other byte kept), and imports those copies.

The originals in `scripts/seed/data/` are never modified, so the dataset stays reproducible. The output goes to **`SEED_OUTPUT_DIR/<SEED_STORE_SLUG>/`**, default `scripts/seed/out/foodmart-benchmark/`, which is **git-ignored** (`.gitignore`: `scripts/seed/out/`). The copies depend on the database (SKUs follow product IDs), so they are regenerated on every run. A database seeded before 2026-11-20 still has `FOODMART-NNNN` SKUs: the mapping is then the identity and the copies equal the originals; no migration is needed.

Season groups use the FoodMart code order from `mapping.csv`, never the SKU, so they do not depend on the order in which products were inserted.

Everything below "Weight v2" can be skipped with `SEED_WEIGHT_V2=0`; the seed then behaves as it did before Weight v2 (no product requires expiry, undated batches of 1,000, no seasons, no weight configuration).

### Why 35% of the products are marked as requiring expiry

`FoodMart_Product_Direct_Insert.sql` marks **all 1,559 products as not requiring expiry** (`requires_expiry = 0`), so F03 U_expiry is always 0 for them and F06 never evaluates expiry. The seed therefore creates a deterministic share (`SEED_EXPIRY_PRODUCT_PCT`, default 35) of the products with `requiresExpiry = true`, decided per FoodMart code by a hash of the random seed. The SQL file itself is only parsed and never changed. Set `SEED_EXPIRY_PRODUCT_PCT=0` to keep every product non-perishable.

### Expiry dates, push days and quantities (perishable products only)

All dates are offsets from `SEED_AS_OF` (default: today in Asia/Ho_Chi_Minh). There is **no automatic push-day rule** (no `expiry − 7`, DEC-20261124-02): the demo mixes batches with and without a push day so the `MISSING_PUSH_DAY` warning is visible (PO, 2026-11-25). Observed on a fresh database with `SEED_AS_OF=2026-11-25` (551 batches, ROC-20261125-004):

| Property | Rule (default) | Observed |
|---|---|---:|
| Expired yesterday / expires today | 3% (`SEED_EXPIRY_EDGE_PCT`), half each; shows `EXPIRED` and `daysToExpiry = 0` (DEC-20261124-01) | 6 expired yesterday (`EXPIRED`, −1); 16 expire today (`ACTIVE`, 0), including some from the 0–7 bucket |
| Expires in 0–7 days | 15% (`SEED_EXPIRY_SOON_PCT`) | 77 (including today) |
| Expires in 8–30 days | 25% (`SEED_EXPIRY_MID_PCT`) | 134 |
| Expires in 31–180 days | the rest | 334 |
| Push day set, spread over expiry − 3…21 days | ~60% (the rest) — `SEED_PUSH_LEAD_MIN_DAYS` / `SEED_PUSH_LEAD_MAX_DAYS` (3 / 21) | 333 (60.4%); a 7-day lead is 25 of the 426 batches with a push day |
| Push day already reached (`pushDay` = as-of date − 0…10 days, never after expiry) | ~15% (`SEED_PUSH_REACHED_PCT`) | 93 (16.9%); 155 batches in total have a push day ≤ as-of date, because some set push days of soon-expiring batches have passed too |
| No push day (`MISSING_PUSH_DAY`) | ~25% (`SEED_PUSH_MISSING_PCT`) | 125 (22.7%); the 123 that are not expired show the warning in the batch API |
| Initial quantity | log-uniform between `SEED_EXPIRY_QTY_MIN_PCT` (2%) and 100% of `SEED_BATCH_QUANTITY` (1,000) | 20 – 994, mean 244 |

`pushDay` is never after the expiry date (the API rejects it otherwise; the test suite checks it). A batch is expired only after its expiry date (DEC-20261124-01): a batch expiring **today** is still sellable, one that expired yesterday is `EXPIRED` and gets no `MISSING_PUSH_DAY` warning. Non-perishable products keep an undated batch of `SEED_BATCH_QUANTITY`. The varied quantity is deliberate: with the same 1,000 units every batch would be at risk and U_expiry would be about 1 for all of them. Total stock is 1,142,397 units (perishable 134,397) instead of 1,559,000.

### Seasons and product groups

The FoodMart data has **one category** and generic product names ("FoodMart Item 0001"), so category names cannot define groups. A group is a block of products in FoodMart code order from `mapping.csv` (position `i/N`), never in SKU order. Weights are configurable.

| Season | State on `SEED_AS_OF` | Dates (offset from `SEED_AS_OF`) | Weight | Product block | Products |
|---|---|---|---:|---|---:|
| Demo: Year-end Sale | active | −14 … +45 days | 0.7 (`SEED_SEASON_ACTIVE_WEIGHT`) | first 30% | 468 |
| Demo: Flash Sale Week | active, overlaps the one above | −3 … +10 days | 0.8 (`SEED_SEASON_OVERLAP_WEIGHT`) | 27% – 40% | 203 |
| Demo: Tết 2027 | future | +55 … +85 days (2027-01-11 … 2027-02-10 on 2026-11-17) | 0.9 (`SEED_SEASON_FUTURE_WEIGHT`) | 40% – 70% | 468 |
| Demo: Back-to-School (ended) | ended | −75 … −30 days | 0.6 (`SEED_SEASON_ENDED_WEIGHT`) | 65% – 85% | 312 |

47 products belong to both active seasons (rule P2: the highest weight, 0.8, applies; the lower season is still listed in `activeSeasons`). The fourth season exists because P2 needs two *active* seasons. Season dates are relative, so a season that already exists keeps its dates when `SEED_AS_OF` changes; the script reports that.

### Weight configuration

`PUT /api/utility/config` as Merchandiser: α = `SEED_WEIGHT_ALPHA` (0.6), β = `SEED_WEIGHT_BETA` (0.4), λ = `SEED_WEIGHT_LAMBDA` (0.3), N = `SEED_WEIGHT_SALES_WINDOW_DAYS` (30). α + β must equal 1. The System Admin λ policy (`lambdaMax`, default 0.5) is left alone unless it is lower than λ; then the seed raises it to λ and says so.

## Running it again, and reseeding

- **Running twice is safe.** Every step looks for its record first: products by their exact name `FoodMart Item NNNN`, batches by "the product already has a batch" (never by batch code, which the backend generates), imports by file name. A second run on a fresh database (2026-11-25) created nothing; a fingerprint of products, batches, seasons, season assignments, imports, transactions, users, Store and category, and `mapping.csv`, were identical before and after. Changing a Weight v2 setting and rerunning changes only the weight configuration (a new configuration version, no duplicates).
- **Reseeding for a clean demo: recreate the database** (for the staging stack, `docker compose … down -v` and start again, or drop and recreate the schema), start the backend so Flyway runs and the bootstrap account is created, then run `seed.sh`. This is the supported way to apply Weight v2 to a database seeded earlier.
- **A database seeded before Weight v2 cannot get expiry dates through the API.** The batch PATCH accepts only `remainingQuantity`, `status` and `pushDay` (no `expiryDate`), and `PUT /api/products/{id}` with `requiresExpiry = true` answers 400 "Cannot require expiry while a batch has no expiry date", even after the batch is blocked and emptied (checked on a real database). The seed therefore keeps the existing undated batches, still creates the seasons and the weight configuration (seasons give W > 1 for 624 products), and prints a warning with the number of products that stay undated (551). It does **not** add a second `SEED-W2` batch: such a batch on a product that does not require expiry has no F03 effect (`NOT_APPLICABLE`) and would only add stock.
- A seed run uses roughly 6–10 logins; the backend limits logins to 30 per IP per 15 minutes, so several runs in a row can answer 429.

## Co-purchase baskets: why the demo has BUNDLE, CROSS_SELL and FBT candidates

The two base files hold random baskets: no product pair is bought together more often than chance, so EFIM returned only single-product patterns and F06 could build nothing but BANNER candidates (smoke test 2026-11-27, defect #1). `data/Transactions_F04_Demo_Copurchase.csv` adds 635 orders (1,613 lines, ids `FMCOP-000001…`) in which four disjoint groups of products are bought together. It is generated, deterministic and committed; the base files are never changed.

| Group | Products (FoodMart codes) | Share of all orders | Gives |
|---|---|---:|---|
| F1 frequent pair | 0212, 1219 | 5.65% | BUNDLE (2), FBT, CROSS_SELL |
| F2 frequent triple | 1557, 1513, 0750 | 5.59% | BUNDLE (2, 3), FBT, CROSS_SELL |
| O1 occasional quad | 0041, 0092, 0551, 0151 | 0.90% | BUNDLE (2, 3, 4), CROSS_SELL |
| O2 occasional pair | 1342, 1525 | 0.67% | BUNDLE (2), CROSS_SELL |

Why these numbers. The default F06 policy (`F06_RULES_V1_1`) decides:

- **BUNDLE** needs a pattern of 2–4 products and no transaction evidence. Any pattern EFIM outputs gives one candidate, so a group of *n* products also gives its sub-groups (O1: six pairs, four triples and the quad). Bundles of different groups never overlap, so the demo can seed Layout B with up to five disjoint bundle blocks (a product may appear once per layout).
- **FBT** needs the whole pattern in at least 2 baskets **and in at least 5% of all baskets of the snapshot** (`minSupportRatio 0.05`). That is why F1 and F2 are frequent (5.2–5.8% on the full range and on every single day) and why O1 and O2 correctly give no FBT. The orders are spread over the four days in proportion to the base data.
- **CROSS_SELL** needs, per anchor product, (baskets with the whole pattern) ÷ (baskets with the anchor) ≥ 0.50. The group products appear in only 3–10 base orders each, so confidence is 0.76–0.96.
- The products are non-perishable and `ACTIVE`, so they stay `ELIGIBLE` (the batches the seed creates are sellable). Quantities are 1–3 (frequent groups) and 2–4 (occasional groups; they need enough utility to pass 0.12%).

The F06 policy is not changed by the seed. A Store Admin can lower `minSupportRatio` (`PUT /api/recommendations/config`), but the demo does not need it.

Regenerate or verify the file (stdlib only, from the repository root):

```bash
python3 -I scripts/seed/generate_copurchase_baskets.py            # write the file
python3 -I scripts/seed/generate_copurchase_baskets.py --check    # fail when the committed file differs
```

The seed imports it like the base files: a copy with server SKUs, imported once (a rerun reports "skipped, already imported"). A database seeded before this change gets only the new file on the next run (the products and the first two imports are skipped), so it needs no recreation; the new orders then count toward every range that includes their days.

## Which date to analyse (important)

The seeded orders are from **2026-10-01 to 2026-10-04**, but the live preview (`GET /api/utility/products/{id}/scores`) and `SEED_AS_OF` use **today**. With the default N = 30 the sales window of a date after 2026-11-02 contains **no orders**, so every perishable product is `SLOW_MOVING` and U_expiry is 0 (only season weights show). Choose one:

- Create snapshots with an `asOfDate` inside the order period, for example **2026-10-05** (the 30-day window then contains all orders). Verified: 221 products with expiry risk, W up to 1.24.
- Or keep the live preview meaningful with `SEED_WEIGHT_SALES_WINDOW_DAYS=48` on 2026-11-17 (the window reaches 2026-10-01); this must grow by one each day, so it is only a stop-gap. Verified: 381 products with U_expiry > 0, W from 1.00 to 1.28, 706 products at W = 1.

## Recommended demo snapshot range and policy for F03 → F05

**Use `rangeStart = 2026-10-01`, `rangeEnd = 2026-10-04`, `asOfDate = 2026-10-05` and the System Admin minUtil policy `PERCENTAGE 0.12`.** On a fresh seed this gives 182 EFIM patterns in about 0.5 s (`LOSSLESS`), and F06 generates 17 BUNDLE, 41 CROSS_SELL, 5 FBT and 182 BANNER candidates (measured 2026-11-27, [ROC-20261127-002](../../docs/record-of-changes/2026-11-27/02-demo-seed-copurchase-baskets.md)). The policy is a System Admin setting (`PUT /api/system/mining/config`); the seed does not set it.

| Range (`asOfDate`) | minUtil | Result | Patterns by size | BUNDLE / CROSS_SELL / FBT / BANNER |
|---|---|---|---|---|
| **2026-10-01..04 (2026-10-05)** | **`PERCENTAGE 0.12`** | **COMPLETED, 182 patterns, 520 ms** | 1: 165, 2: 11, 3: 5, 4: 1 | **17 / 41 / 5 / 182** (at most 5 BUNDLE candidates are pairwise disjoint) |
| the same | 0.14 / 0.10 | 100 / 316 patterns | the same 17 multi-product patterns | 17 / 41 / 5 / 100 and 316 |
| the same | 0.09 / 0.08 | 419 / 862 patterns, still below the 2,000 limit | adds large patterns from the 10–14-line orders (sizes 5–14) | 18 / 41 / 5 / 419 and 862 |
| the same | 0.25 | 22 patterns | 1: 6, 2: 10, 3: 5, 4: 1 | 16 / 39 / 5 / 22 |
| 2026-10-01..03 (2026-10-03) | 0.12 | 183 patterns | 1: 166, 2: 11, 3: 5, 4: 1 | 17 / 41 / 5 / 183 |
| 2026-10-02 only (2026-10-05) | 0.25 | 111 patterns | 1: 9, 2–4: 16, 10–14: 86 (from the few 10–14-line orders) | 16 / 116 / 5 / 111 |
| 2026-10-02 only (2026-10-05) | 0.12 | `FAILED OUTPUT_LIMIT` (more than 2,000 patterns) | – | – |

- The multi-product patterns are the four co-purchase groups below, and all candidates are `ELIGIBLE` (non-perishable products with stock). Patterns of size 5–14 appear only at 0.09% and lower, or on a single day; they come from the few base orders with 10–14 lines, and F06 skips them for BUNDLE (`BUNDLE_EXCEEDS_MAX_SIZE`).
- The conversion stays `LOSSLESS` for every range above: the divisor handles the larger total (54,626,020.11 on the full range). F05 falls back to whole đồng only on an int32 overflow (DEC-20261119-05).
- A snapshot may hold at most 20,000 matrix rows. The full range has 19,932 (18,319 base + 1,613 co-purchase lines), so there is little room left: do not add more orders to the full range without checking `scripts/seed/tests/test_copurchase_baskets.py`.
- Before the baskets existed (2026-11-27, same stack): the full range at `PERCENTAGE 0.12` gave 180 patterns, all single-product, so F06 produced BANNER candidates only; `0.10` gave 326 patterns with two large patterns of size 13 and 14.

## TDP-01: Store B and Store C for the black-box test round

`seed_test_stores.py` (run it with `seed_test_stores.sh`) is the test-data preparation script TDP-01 of [TEST_PLAN §6](../../docs/testing/blackbox/TEST_PLAN.md) (DEC-20261126-03, Q-16): testers do not create Stores by hand, so running it is an entry criterion of the round. Public REST API only (no SQL), signed in as the System Admin; the OTP of each invitation is read from Mailpit, as in the demo seed.

| Created | Through |
|---|---|
| Store B `QA Store B` (slug `qa-store-b`), Store C `QA Store C` (slug `qa-store-c`) | `POST /api/system/stores` |
| `qa-storeadmin-b@paspm.example`, `qa-merchandiser-b@paspm.example` (Store B) | `POST /api/users`, then `POST /api/auth/activate` with the `ADMIN_INVITE` OTP |
| `qa-storeadmin-c@paspm.example`, `qa-merchandiser-c@paspm.example` (Store C) | the same |

```bash
# scripts/seed/.env.seed: SEED_API_URL, SEED_MAILPIT_URL, SEED_SYSADMIN_EMAIL/PASSWORD and SEED_TEST_ACCOUNT_PASSWORD
scripts/seed/seed_test_stores.sh            # or: scripts/seed/seed_test_stores.sh path/to/other.env
```

- Run it on the disposable ENV-1 backend (bootstrap System Admin, Mailpit reachable). `SEED_TEST_ACCOUNT_PASSWORD` is one password for the four accounts (backend password rules); it is read from the environment, never printed or written.
- **Safe to run twice.** A Store is found by slug (`status=ALL`) and an account by e-mail (a login with the configured password) before anything is created; the second run creates nothing. A pending account of an interrupted run gets a new OTP instead of a second invitation. An **INACTIVE** Store stops the script with a message (it never reactivates a Store); an account that exists but does not accept the configured password is left alone and stops the script.
- It prints one line per Store (with its `storeId`) and per account (`created` / `found`) for the run record, and no password.
- The catalogue, snapshots, mining requests and icons of Stores B and C are not created here (TEST_PLAN §6, SETUP-B and DP-07).

## Tests

The date, push-day, quantity, season and configuration rules are pure functions in `weight_v2_plan.py`; the FoodMart code → SKU mapping and the CSV rewrite are pure functions in `foodmart_mapping.py`. Their unit tests need no backend:

```bash
python3 -I -m unittest discover -s scripts/seed/tests -v
```

`tests/test_copurchase_baskets.py` proves from the data files that the committed basket file is what the generator produces, that the base files are unchanged, and that the F06 FBT and CROSS_SELL arithmetic and the 20,000-row limit hold. `tests/test_seed_test_stores.py` covers TDP-01 (request bodies and idempotency, with the HTTP layer faked). The remaining demo-seed script (HTTP calls) is covered by verification runs, not by automated tests: record 014 (2026-11-17) and [ROC-20261125-004](../../docs/record-of-changes/2026-11-25/04-sku-foodmart-seed.md) (fresh MySQL 8.4, two runs).
